# Sayable — latest visual review (November 8, 2026)

This folder contains four USER-PROVIDED current-site screenshots. It supplements the earlier `docs/sayable_design_feedback` packet. These screenshots are feedback references, not proof of current code; inspect working tree and render live website as authoritative.

## Primary user decision

**Restore the earlier document reading-structure scan across the hero, and link that same object and scan path continuously into the inventory/multiplication, prioritization, repair, verification, and closing sequences.** The user likes the idea of that scanner, but not the bland font, extreme darkness, weak readability, isolated sections, or repeated patterns.

## Precise screenshot findings

### 01-current-hero-washed-out-scan.png

Current hero: giant pale headline/subheading and pale CTAs, scan line crossing a municipal PDF; restore scanning effect but make text readable, line intentional and no flickery low-opacity hold.

### 02-filename-monospace.png

Current permit-application.pdf label: monospaced filename is overly emphasized; use metadata typography sparingly.

### 03-repair-scene-near-black.png

Current dark repair scene: PDF too small relative to space; supporting headline, body and play control are nearly invisible due to very low contrast; heavy black transition, tiny semantic text.

### 04-scale-scene-abrupt-black.png

Current inventory scale scene: one document over field of tiny document thumbnails, large white serif headline on black, detached tiny decorative stage pills. Keep document multiplication but integrate with scanning hero; reconsider all-black background and type style.

## Required changes

1. Recover the earlier working scan/reading-order hero from Git history or available source rather than approximate from scratch. Keep behavior and progressive animation but rewrite hierarchy and add a single shared visual narrative.
2. Perform an honest, screenshot-based font exploration across at least 4 licensed, non-generic type systems. Separate expressive display use from accessible long-form body use. Replace the clashing serif/mono/sans combinations.
3. Avoid prolonged text opacity below readable contrast. Evaluate actual scroll frames, including reversing, fast scrolling, low-power devices and reduced motion.
4. Reconsider hard white-to-near-black jumps; use deep mineral, ink, or tonal backgrounds only if justified, with smooth deliberate scene transitions. The site needn't be mostly white nor mostly black.
5. Dramatically improve the repair scene's contrast and product scale; keep narration controls accessible and readable.
6. Show document count and organizational scale without 100s of indistinguishable tiny rectangles; use perspective, grouping, depth, restrained motion and useful labels.
7. Remove unnecessary technical labels, mono headlines, ornamental pills/counters, click-dependent story steps, and redundant prose. The main story should advance via native scroll and remain readable without motion.
8. Use actual reference sites, relevant skills, and browser-based screenshot/video verification rather than claiming inspiration without checking them.
9. Maintain honest, testable product claims, government-buyer clarity, WCAG-friendly interactions and performance.
10. Preserve the existing app and deploy only an isolated tested preview.
